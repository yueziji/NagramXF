# Telegram 会话列表断档：自助诊断流程

本版用于调查“会话列表缺少一段日期的聊天，搜索并打开后，重启才能看到；有时几小时后自行恢复，又再次出现”的问题。它采集证据，尚未修复或确认断档根因。

本次观察目标：Android 上 **2026 年 4—7 月**的一段会话从全部聊天及分类文件夹中缺失，桌面端正常。这里的日期是列表里会话最后一条消息的日期；打开会话后的历史消息是否完整，需要另外核对。

## 1. 安装并记录首次加载

- 应用名称：**Nagram XF 诊断版 / Nagram XF Diagnostics**。
- 独立包名：`fork.risin42.nagramx.diagnostics`，可与原版同时安装。两者不共享本地数据库，需要在诊断版重新登录同一账号。
- APK：**arm64-v8a，Android 8.1 及以上**。从 GitHub Actions 的 `Dialog diagnostics APK` 构建下载 `nagram-dialog-diagnostics-arm64` 附件并解压。
- **专用诊断默认开启**，在首次启动、登录和第一批会话加载之前开始记录。无需先找到开关，也无需开启“关于”页里的通用日志。
- 登录后先观察“全部聊天”及出现问题的分类文件夹。首次登录不一定自动加载所有历史会话；向列表底部滚动，让正常分页继续加载，记录仍然存在的日期缺口。

诊断入口：**Nagram 设置 → 关于 → 聊天列表诊断**。不同语言下也可寻找 `Chat list diagnostics`。该项显示“记录中”“已暂停”或“记录已达上限”。

独立包名带来的限制：诊断版从新的本地数据库开始。如果原版故障依赖旧数据库或旧分页状态，新安装时可能无法复现。保留原客户端作对照，不要据此判断问题已解决。

## 2. 先保存断档现场

发现缺口后，先保持现状，避免批量搜索打开所有缺失会话，否则会把它们逐个补回，失去对照。

1. 进入“聊天列表诊断”，点击 **采集当前状态**。
2. 点击 **导出诊断报告**，在系统文件选择器中保存，建议命名为 `01-首次加载-仍有断档.jsonl`。
3. 简单记下：故障发生时间和时区、缺失日期范围、受影响文件夹、电脑端同一会话是否可见。无需提供用户名、手机号或聊天正文。

先导出这一份，再进行后续检查，可以保留最接近首次出现问题的记录。

## 3. 对照服务器列表

1. 点击 **对照服务器聊天列表（只读）**。
2. 保持应用运行，等待“对照完成”或“对照未完成”的提示。
3. 再次导出，建议命名为 `02-服务器对照.jsonl`。

这个检查单独请求主列表、归档及置顶会话，使用自己的分页位置。返回结果只用于诊断，不调用正常会话入库、列表合并、已读标记或重置功能，也不改动原来的分页位置。期间应用自身的常规同步仍可能运行，因此报告保留每步时间。

检查最多读取每个列表 100 页，每页最多 100 个会话。出现请求错误、重复游标、缺少分页信息、记录暂停或达到上限时会中止。**“检查未完成”不能作为“服务器上没有某个会话”的证据**；仍可导出报告查看中止原因。

## 4. 只补回一个会话，比较重启前后

从电脑端或记忆中选两个缺失会话，自己称为 A、B 即可：

1. **只搜索并打开 A**，等消息加载结束。B 暂时保持未打开，作为对照。
2. 返回列表，观察 A 是否已出现。采集状态并导出 `03-打开A-重启前.jsonl`。
3. 按平常的方式结束应用进程，再打开诊断版。
4. 检查 A 和 B 是否出现在“全部聊天”和相应分类中。
5. 采集状态并导出 `04-打开A-重启后.jsonl`。

记录会追加到原文件，匿名会话编号在同一次安装中跨重启保持一致。导出的后续报告包含之前保留下来的记录，可以串起整个过程。

## 5. 如果自行恢复或再次复发

- 刚发现自行恢复时，尽快采集状态，导出 `05-自行恢复.jsonl`。
- 再次复发时，先检查 **已补回的 A 是否又消失、未打开的 B 是否有变化**，然后采集状态，导出 `06-再次复发.jsonl`。
- 如果同时使用官方 Android、Telegram X，记下它们是否在近似时间出现或恢复。没有同时检查就写“未知”，不要根据先后打开应用的结果推断它们同时变化。

优先在取证完成后再考虑“Reset Dialogs / 重置会话”、清除应用数据、退出账号或重装。这些操作会改变本地现场；Reset Dialogs 在当前源码中会清理并重建普通会话的本地缓存。

## 6. 报告记录什么

报告为一行一条事件的 UTF-8 JSONL 文件，主要包含：

- 记录时间、进程运行编号、账号槽位、请求编号。
- 分页日期、会话数量、请求错误码、加载中和结束标志。
- 会话及消息的匿名编号，例如 `p_…`、`m_…`。
- 某个会话是否出现在服务器回包、数据库或当前内存列表。
- 自动重建列表、暂停记录、记录达到上限等事件。

不记录消息正文、用户名、手机号、原始会话 ID、原始消息 ID、访问哈希、登录密钥或完整请求/响应。匿名化种子仅留在该应用的私有目录中，不随报告导出；报告不会自动上传。

报告仍包含活动时间、会话数量等诊断元数据，应只分享给参与诊断的人。不要用普通日志、数据库导出或整个应用数据目录替代这份专用报告。

记录文件上限为 32 MiB，到达后保留已有内容并停止追加，不覆盖最初登录的证据。此时先导出现有报告。`export_status.full=true` 或 `dropped>0` 表示证据可能不完整；`dropped` 是当前进程统计，不能当作全部历史丢弃数量。

## 7. 如何初步判读

这些判断需要结合事件时间、同一账号和同一个匿名会话编号，不能只看一个计数。

| 报告中的现象 | 优先检查方向 |
| --- | --- |
| 普通加载 `page_dialog` 已包含 A，随后数据库检查仍显示 `exists=false` | 入库路径、事务或会话过滤；先确认相应写入已完成 |
| 数据库中有 A，但 `peer_memory` / `applied_dialog` 显示不在内存或列表中 | 内存列表合并、筛选和刷新 |
| 完成的只读检查中有 A，普通加载没有 A | 两条请求的分页边界、folder 参数或结束判断差异 |
| `tail_candidate.matches_oldest=false` | 当前响应中最早消息与列表末尾会话不一致，需检查实际选择的下一页位置；这一条本身不证明跳页 |
| `cursor_decision.same_message_id=true` 且 `same_peer=false`，随后 `cursor_state.exhausted=true` | 可能把不同会话中的相同消息 ID 当成重复游标，提前结束 |
| `list_error` 后，同一列表反复出现 `load_attempt.loading=true`，没有新的成功请求 | 请求失败后的加载状态可能未释放 |
| `reset_from_difference` → `database_reset_begin`，之后 A 从重建结果中消失 | 同步触发的列表重建路径；要区分仍在加载的中间状态和完成后的缺口 |
| 完成的只读列表检查没有 A，但单独打开 A 的 `peer_response` 能取到它 | 需进一步核对列表接口与单会话接口的参数、时序及服务端返回；不代表聊天已删除 |

`source`：`1` 普通网络列表，`2` 本地缓存，`3` 单会话补取，`4` 只读对照，`5` 重建列表请求。`folder`：`0` 主列表，`1` 归档；它们不是“群组”“bot”等自定义分类的编号。

`history_open` 或 `peer_request` 标出你打开的会话匿名编号。`run` 在重启后会变化；匿名编号不会变化。`request` 在相应事件中用于关联一次请求或检查批次，不同处理阶段应结合时间和会话匿名编号对照。

只有记录完整、`probe_end.complete=true` 且各列表检查完成，才能对该次只读扫描作完整性判断。过程中新增消息、会话移动或服务端状态变化也可能造成前后差异。

可选：在 Windows PowerShell 中查看关键事件摘要。将路径改为你的**专用诊断报告**路径：

```powershell
$report = Get-Content -LiteralPath '.\nagram-dialog-diagnostics.jsonl' | ConvertFrom-Json
$report | Where-Object {
    $_.event -in @('process_start', 'list_error', 'cursor_decision',
        'reset_from_difference', 'database_reset_begin', 'probe_end', 'export_status')
} | Select-Object time_ms, run, event, source, folder, count, code,
    same_message_id, same_peer, complete, full, dropped
```

## 8. 版本范围与验证边界

- 专用开关只在 `diagnostic` 构建中默认开启；常规版本默认关闭，不显示该入口。
- 原有分页与同步逻辑保留，便于观察故障。本版增加观察点和独立对照，不自动执行修复。
- 独立包尚未注册 Firebase，禁用该构建的 Firebase 配置及 Crashlytics。前台登录和聊天同步使用 MTProto；**FCM 后台推送不能作为与原版完全等价的对照条件**，优先在前台复现，并记下是否经历长时间后台。
- GitHub 构建会执行匿名化、跨重启保留、容量限制及对照分页的单元测试，并核对 APK 包名和签名。实际账号能否复现、首次登录及手机上的完整操作流程，仍需按本文执行。
